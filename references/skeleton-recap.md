# 战报骨架（recap，11 槽位）

用于：活动结束后的对外战报页。碎片来源通常是复盘文档、问卷、群聊记录、讲者逐字稿、现场相册。

槽位顺序就是页面顺序，**写死在 `assets/opb/skeleton.py` 的 `SKELETONS["recap"]`，`outline.json` 不能自己重排**。原因见下面的排序规则。

## 碎片互相矛盾时怎么办

复盘文档、问卷、群聊记录、讲者逐字稿这几种来源经常互相打架：复盘文档写的到场人数和群聊里现场统计的不一样，早期问卷草稿和收官后的正式统计结果对不上，讲者逐字稿的头衔和活动一页纸上的不一致。**不存在"自动判断哪份对"这种事，但也不能碰到冲突就卡住不产出。按下面三条走：**

1. **新的赢，不临场重新权衡。** 判断"新"优先看碎片自带的时间信号——文件名里的日期/版本号、修订记录、消息时间戳；没有显式时间信号时，内容更具体、被其他独立碎片交叉印证次数更多的那一份，通常就是更晚定稿的那一份。两份都不含糊时才需要人工判断，不要在此之前就自己纠结。
2. **两个版本都要在闸门一报告里点名，不能只写赢的那份。** 输给了的那份要写清楚"我读到了 X，选了 Y，因为 Z"——人工审阅者可能知道 X 才是真的还没同步给你，而你没有渠道验证这件事，报出来才能被纠正。
3. **不做"各取一半拼起来"的静默合并。** 两份数据对不上时，选一份整体使用并注明另一份的存在，不要把两个不同来源的数字拼成一份两边都没实际统计过的第三个数——那个数字不对应任何真实统计，事后没有办法追溯错在哪一半。

## 排序规则（蓝军第 10 条，必须遵守）

| 情况 | 必须怎么排 |
|---|---|
| 多个奖项/成果与普通内容同屏 | 获奖 > 能用（可复用的产出）> 其他 |
| 亮点内容与过程记录同屏 | 亮点 > 过程 |
| 想按组号、时间线、内部表结构排序 | **禁止**——读者不知道组号是什么，时间线是内部记忆脚手架不是读者的关心顺序 |

排序依据永远是"读者关心程度"，不是"我们当初怎么记录的"。

## quote-ticker 长图不可用

`quote-ticker`（双行滚动原声，web 专属）**没有替身**，不能在 `longpic` 版 outline 里出现。原因：滚动轮播依赖"时间"这个维度才能成立，长图是一张静态图，没有时间轴，硬性截一帧毫无意义（决策 D10：直接删，不降级成静态列表）。`buzz` 槽位如果只放了 `quote-ticker`，写 `longpic` 版 outline 时必须换成 `quote-card`（下方逐条列出原声卡），不能留空、也不能指望 build 自动转换——build.py 撞到这种缺替身的情况会直接抛 `BuildError`，不会静默丢内容。

## 原声类组件的文本必须手动包「」，否则拿不到验证与豁免（Task 15 F2）

`quote-card`（以及 `keynote-block` 这类可能承载"逐字引用"的组件）**不会自动**给 `text`/`paras` 加上 `「」`——`_quote_card` 的渲染函数只是把字符串原样放进 `<p>` 标签，`「」`要不要出现完全取决于 outline 作者有没有在 JSON 字符串里手动打上这两个字符。这件事此前完全没有写在任何文档里，是 Task 15 用真实执行验证出来的：

- **层1（引用逐字）** 只提取页面文本里字面 `「...」` 配对的内容去和语料比对——不加 `「」`，一段完全编造、语料里从未出现过的话放进 `quote-card.text`，层1返回零发现，编造内容完全没被查过。
- **层3（黑话）/层4（AI 味）** 都读 `ctx.text_noquote`（`strip_quoted()` 抹掉 `「...」` 区域后的文本）——不加 `「」`，一句真实的、逐字来自参会者的原声，只要恰好撞上黑名单词或"不是…而是…"这类构式，就会被误判成本方违规文案，即使这句话一个字都不是自己写的。

**结论：outline.json 里任何要享受"这是verbatim引用，不受黑话/AI味检查约束"待遇的文本，必须自己在 JSON 字符串里手动写 `「实际引用内容」`，组件不会替你做这件事。** 反例（已发现的真实案例）：`SPEC.example/sh-invite/outline.json` 的 `quote-card`（盛保桦"真的特别棒！！气氛超热烈！"）没有包 `「」`——这条引用从未被层1真正校验过，只是恰好这条引用本身是真的、且不含AI味模式，侥幸没有暴露问题。**这个历史遗留不在本次修复范围内，如实记录，不回头改那个页面。**

## 跨体裁通用组件

以下 5 个组件不属于战报专属，`assets/opb/components/common.py` 里注册，邀请函和通用页也在用：

| 组件 | 用途 |
|---|---|
| `sysbar` | 顶部信息条（一行文字，如活动名+日期） |
| `section-head` | 区块标题（眉标 + 大标题） |
| `atm-layer` | 氛围光晕层，无内容槽位，纯装饰，铺在区块背景 |
| `footer-brand` | 页脚品牌区，longpic 模式自动把 logo 从 104px 收小到 74px |
| `reveal-wrap` | 滚动渐显包裹层，longpic 模式自动关闭动效（长图必须全部可见，不能靠滚动触发） |

组件注册表是全局共享的（`assets/opb/components/base.py` 的 `_REGISTRY`），不按体裁隔离——下表只是每个槽位的**典型**搭配，不是强制限定。`outline.json` 的合法性只由 `validate_outline` 检查槽位顺序与必备项，不检查槽位里塞了哪个具体组件；需要时可以跨体裁借用邀请函的组件（比如 `works` 槽位想用 `terms-list` 列产出清单也是合法的）。

## 每个数字都要能自证（蓝军第 6 条，结构性强制）

`stat-caption` 组件的 `caption` 是必填槽位——留空会在渲染阶段直接抛 `SlotMissing`，不是等断言层才发现。写 `outline.json` 时，每个数字条目必须同时给 `value`／`label`／`caption` 三样，`caption` 是"让没参加过的人一眼看懂这个数字为什么值得说"的一句话，不是数字的重复。这个字段最终要与 `facts.json` 里同一条 fact 的 `caption` 对得上（见 `references/verify.md` 层 2）。
