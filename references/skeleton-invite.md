# 邀请函骨架（invite，9 槽位）

用于：活动前的对外邀请函页。碎片来源通常是执行会逐字稿、讲者 Base、往届数据、群聊讨论。

槽位顺序就是页面顺序，写死在 `assets/opb/skeleton.py` 的 `SKELETONS["invite"]`，`outline.json` 不能自己重排。

## 碎片互相矛盾时怎么办

碎片来源多、时间跨度长，同一件事被写过不止一次是常态：执行会逐字稿说 A，三天后的策划 wiki 说 B；参会指南上的议程和最新的策划文档对不上；同一位讲者的头衔在两份文档里被抄错、抄反。**不存在"自动判断哪份对"这种事，但也不能碰到冲突就卡住不产出。按下面三条走：**

1. **新的赢，不临场重新权衡。** 判断"新"优先看碎片自带的时间信号——文件名里的日期/版本号（`_latest`、`_v2`、`_0729b` 这类）、修订记录、消息时间戳；没有显式时间信号时，内容更具体、被其他独立碎片交叉印证次数更多的那一份，通常就是更晚定稿的那一份（早期草案往往更粗略，细节是后补的）。两份都不含糊时才需要人工判断，不要在此之前就自己纠结。
2. **两个版本都要在闸门一报告里点名，不能只写赢的那份。** 输给了的那份要写清楚"我读到了 X，选了 Y，因为 Z"——人工审阅者可能知道 X 才是真的还没同步给你，而你没有渠道验证这件事，报出来才能被纠正。
3. **不做"各取一半拼起来"的静默合并。** 两份议程结构不同、环节数量不同、讲者分工不同时，选一份整体使用，不要把 A 的开场时间和 B 的讲者阵容拼成一份两边都没实际存在过的第三版——那份拼接结果不对应任何真实计划，事后没有办法追溯错在哪一半。

这条规则同样适用于判断"某份文档还有没有在被使用"：一份对外发出去过的旧参会指南，哪怕内容被更新的策划文档超越了，也可能已经被读者看到过——按第 2 条把这个疑虑写进报告，不要自己直接假定旧版本已经作废。

## 跨体裁通用组件

以下 5 个组件不属于邀请函专属，`assets/opb/components/common.py` 里注册，战报和通用页也在用：

| 组件 | 用途 |
|---|---|
| `sysbar` | 顶部信息条（一行文字，常用来放"仅限 XX 人 / 报名截止日期"这类身份戳） |
| `section-head` | 区块标题（眉标 + 大标题） |
| `atm-layer` | 氛围光晕层，无内容槽位，纯装饰 |
| `footer-brand` | 页脚品牌区，longpic 模式自动收小 logo |
| `reveal-wrap` | 滚动渐显包裹层，longpic 模式自动关闭动效 |

组件注册表全局共享，不按体裁隔离——下表是每个槽位的典型搭配，不是强制限定。例如 `proof` 槽位想呈现"上一站数字"，可以直接借用战报体裁的 `stat-caption` 组件，不需要邀请函自己重新发明一个数字组件。

## 9 槽位

| 槽位 key | 内容 | 必备 | 规则 | 典型组件 |
|---|---|---|---|---|
| `hero` | 身份戳 + 主标题 + 副标 + 信息卡 | ✅ | 信息卡（日期/时间/地点/席位）标签一律用中文，不用 `DATE`/`VENUE` 这类装饰性英文（黑名单基线已列入禁用词） | `sysbar` `section-head` `info-meta` `atm-layer` |
| `why_you` | 稀缺性论证 + 重锤块 | ✅ | 重锤块 = 全场唯一不可替代的那件事，不是泛泛的"值得来"话术 | `hook-grid` `keynote-block` |
| `agenda` | 时间 + 环节名 + 一句白话 | ✅ | 环节名要有信息量，不能是"环节一""环节二"这类占位编号 | `agenda-rows` |
| `value` | 亮点卡 / 对谈卡 | ✅ | 卡片钩子句写**反差**，不写人物介绍——参考真实案例句式"一个说还早，一个已经把 CTO 裁了" | `talk-card` |
| `people` | 讲者：姓名 + 头衔（+ 链接） | ✅ | 讲者主页/社媒外链必须做三特征比对（姓名+头衔+机构三者都对上）才能采信，不能凭标题相似就用 | `talk-card` `info-meta` |
| `hook` | 现场独有的可感物 | ○ | 具体到"四杯酒 / 摊位 / 训练室"这类可触摸的现场元素，不写抽象氛围词 | `hook-grid` `keynote-block` |
| `proof` | 上一站数字 + 战报链接 | ○ | 数字须带 `caption`；如果要放可点击的战报链接，纯数字用 `stat-caption`（它没有链接槽位，装不下这条规则要求的链接），链接本身用 `quote-card` 的 `link` 槽位（例如"较上一站——[更多看这里](链接)"这类带原声的引用式链接） | `stat-caption`（纯数字，借自战报组件集）+ `quote-card`（需要链接时用，同样借自战报组件集） |
| `terms` | 带什么 / 门槛 / 传播尺度 | ✅ | 把禁区包装成特权来写，不写成限制条款的口吻 | `terms-list` |
| `cta` | 行动入口 | ✅ | **网页版 = 按钮，长图版 = 二维码，二者是同一个槽位的两种模式替身，见下节。** 页脚品牌区（`footer-brand`）不是独立槽位，它是跨体裁通用组件，惯例上作为本槽位 `components` 数组的最后一项跟在 `cta-pills`/`qr-closure` 之后——视觉上页脚本来就跟在页面最后一个区块之后，和战报骨架 `next` 槽位收 `footer-brand` 是同一个道理（见 `references/skeleton-recap.md`） | `cta-pills`(web) ↔ `qr-closure`(longpic)，末尾可选追加 `footer-brand` |

## `cta` 槽位的 web/longpic 替身机制（S1 + S8）

`cta` 是本骨架里唯一一个网页版和长图版渲染完全不同组件的槽位，原因是长图交互归零（S1）：静态图片点不了按钮，任何"点击跳转"的行动方式在长图里都不成立，必须换成二维码闭环（S8，见 `references/longpic.md`）。

`cta-pills` 与 `qr-closure` 各自的 `modes` 声明是互斥的：

| 组件 | `modes` | 数据槽位 |
|---|---|---|
| `cta-pills` | `("web",)` 仅 web | `title` `text` `buttons`（按钮数组，每个含 `label`/`href`） |
| `qr-closure` | `("longpic",)` 仅 longpic | `qr`（二维码图片路径） `alt` `lines`（提示文案） |

`outline.json` 里同一个组件条目要同时支撑两种 build 模式，写法是给组件本体配一个 `longpic` 替身块（`build.py` 按目标 mode 优先取替身）：

```json
{
  "key": "cta",
  "components": [
    {
      "name": "cta-pills",
      "data": {"title": "报名入口", "text": "席位有限，先到先得",
               "buttons": [{"label": "立即报名", "href": "https://example.com/rsvp"}]},
      "longpic": {
        "name": "qr-closure",
        "data": {"qr": "assets/qr.png", "alt": "报名二维码",
                 "lines": "扫码报名 · 2026.08.15 · 北京"}
      }
    }
  ]
}
```

同一份 `outline.json` 分别喂给 `build(mode="web")` 和 `build(mode="longpic")`：web 构建时用组件本体 `cta-pills`，longpic 构建时自动取 `longpic` 替身 `qr-closure`——不需要手写两份 outline，也不需要在构建脚本里写 if/else 判断体裁。

**如果漏配 `longpic` 替身会怎样**：`build.py` 在 longpic 模式下发现 `cta-pills` 不支持该模式且没有替身，直接抛 `BuildError`，报错文案会点名"已知替身是 `qr-closure`"——不会静默丢掉整个 CTA 区块，也不会硬把网页按钮糊进长图里点不动。
