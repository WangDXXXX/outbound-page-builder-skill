# 设计系统注入：三形态 → 统一令牌层

本 Skill 不生成设计系统，只接受注入。三种输入形态，一种输出：`theme/tokens.css` + `theme/RULES.md`。组件库只认这两个文件，换设计系统 = 换这两个文件，组件代码一行不动。

## 三种输入形态

| 形态 | 长什么样 | 处理方式 |
|---|---|---|
| A 四件套文件 | 一个目录，含 `.md`（设计说明）+ `tokens.json` + `theme.css` + `variables.css` | `theme.from_fourpack_detailed(目录路径)` |
| B 一段风格描述 | 用户直接打字描述色板/字体/形状（没有文件） | 人工把描述转成一份最小 `tokens.css`（哪怕只写 `--bg`/`--accent` 两三个变量），再走形态 A 或 C 同一套规约器 |
| C 前作继承 | 指定一个已经上线的 HTML，从里面反抽 `:root` 变量 | `theme.from_prior_page(html_路径)`——如果那个页面本身已经用的是本 Skill 的 19 个统一令牌名，直接原样复用；不是的话走同一套三阶段映射 |

三种形态最终都落到同一个函数 `theme.emit_tokens_css(mapping)`，产出 `:root { --bg: ...; ... }` 形式的 `tokens.css`。`RULES.md` 是人写的，不是程序生成的——三形态里能自动抽的只有颜色变量，色板之外的规则（形状克制程度、品牌固定件怎么处理）需要人读一遍原始设计说明后填写。

## 19 个统一令牌（组件只认这些名字）

```
--bg --bg-2 --bg-sunken
--fg --fg-2 --fg-3
--hair
--accent --accent-2
--invert-bg --invert-fg
--font-cn --font-mono
--radius-s --radius-m --radius-l
--pad --gap --maxw
```

| 令牌 | 角色 |
|---|---|
| `--bg` | 页面画布底色 |
| `--bg-2` | 卡片/次级容器底色 |
| `--bg-sunken` | 凹陷区域底色（比画布更深一级） |
| `--fg` | 主文字色 |
| `--fg-2` | 次文字色 |
| `--fg-3` | 弱文字色/注脚 |
| `--hair` | 发丝线，1px 分隔线颜色 |
| `--accent` | 唯一强调色，配给制使用，不能大面积铺底 |
| `--accent-2` | 仅"高潮时刻"可用的第二强调色，没有独立第二强调色时等于 `var(--accent)` |
| `--invert-bg` | 亮色反转段背景（暗色页面里偶尔出现的亮底区块） |
| `--invert-fg` | 亮色反转段文字色 |
| `--font-cn` | 中文正文字体栈，必须包含 CJK 字形覆盖（PingFang SC / Hiragino Sans GB / Microsoft YaHei 这类） |
| `--font-mono` | 数字/英文缩写专用字体栈，只用于"读数"场景，不跑中文正文 |
| `--radius-s` / `--radius-m` / `--radius-l` | 圆角三级，小于中于大，不能倒挂 |
| `--pad` | 页面左右留白 |
| `--gap` | 区块之间的垂直间距 |
| `--maxw` | 正文最大宽度 |

这套名字是四份历史实例（Dope Security / Hyperstudio / Ciridae + 一份前作继承）的公因式：**暗底 + 一个配给制强调色 + 发丝线 + mono 只做数字 +（可选）亮色反转段 +（可选）高潮色**。任何缺项由 `theme.emit_tokens_css()` 用内置默认值兜底（发丝线用半透明白、圆角用 6/10/16px、留白用 20/56/1240px），保证组件永远拿得到全部 19 个变量，不会因为设计系统没提供某个令牌就渲染出裂开的 CSS 声明。

## 三阶段映射：为什么必须可审阅

`theme.py` 按顺序跑三个阶段，映射每一个统一令牌：

1. **按名字线索**（`stage='name'`）——原始变量名里出现 `void`/`abyss`/`ember`/`bone` 这类语义词，直接按同义词表对应到统一令牌。
2. **启发式后备**（`stage='heuristic'`）——名字线索没覆盖到的令牌，按亮度/饱和度排序猜测角色（最深色当 `--bg`，最浅色当 `--fg`，饱和度最高且亮度适中的当 `--accent`）。
3. **内置默认**（`stage='default'`）——前两阶段都没填上的令牌，用 `_FALLBACK` 兜底值。

**启发式会猜错，而且猜错的方式很危险：强调色只要亮度落在中段，就会持续与弱文字色槽位碰撞**——这不是阈值没调好，是"按亮度/饱和度猜角色"这个方法本身有结构性盲区，任何阈值都救不了（历史踩坑：Ciridae 的强调色曾被启发式错判成弱文字色，整页强调色变成了正文颜色）。没有任何一种自动规则能覆盖用户随手拿来的设计系统，因为设计者从没为"被程序猜角色"设计过变量名。

**所以映射结果必须在闸门一展示给人确认，不能静默采信。** `theme.describe(mapping, sources)` 产出一张表，每一行是"令牌 → 值 ← 来源"：

```
--bg            #0b0b0b              ← name
--bg-2          #272a2a              ← name
--accent        #cc6437              ← name
--fg-3          #484848              ← name
--accent-2      var(--accent)        ← default
...
```

`← heuristic` 和 `← default` 的行必须重点看一遍——这两类是程序猜的或兜底的，不是设计系统原文直接给出的。**这张表必须原样贴给用户，问一句"这个映射对不对"，用户确认后才能进入组件拼装**，不能因为程序跑完没报错就当作映射天然正确。

## 三条硬不变式（映射违反直接报错，不会产出"能跑但难看"的结果）

- `--accent` 不能等于 `--fg`/`--fg-2`/`--fg-3` 中任何一个（强调色不能悄悄变成一个文字色）。
- `--bg` 不能等于 `--fg`（画布和主文字不能同色，否则全页不可读）。
- `--invert-bg` 的亮度必须高于 `--bg`（反转段存在的意义就是"比画布更亮"，亮度不够就不是反转段）。

违反任何一条，`theme.ThemeError` 直接抛出，不会返回一份看起来能跑、实际上强调色糊在文字上的映射。

## `RULES.md` 五节结构（+ 可选第六节）

沿用本项目历史上已经验证过的结构，`assets/presets/*.RULES.md` 两份兜底预设也按这个结构写：

1. **色板**（不新增色相）——列出全部 19 个令牌的实际取值，声明"除已列出的强调色相外不允许出现第三个彩色色相"。
2. **字体层级**——`--font-cn`/`--font-mono` 各自的适用场景，中文字号不得小于同屏英文/数字。
3. **形状与体积**——圆角三级、间距三级的实际数值，以及这套设计系统的形状语言是"柔和大圆角"还是"克制近直角"。
4. **品牌固定件**——logo/贴纸等资产的使用规则（官方原始文件、不抠图不改色）。
5. **禁令**——这套设计系统明确不允许的做法，逐条列出。
6. **〔可选〕高潮时刻**——`--accent-2` 存在独立取值时，说明它能且只能在什么场景破戒使用；不存在独立取值（等于 `var(--accent)`）时说明这套系统没有传统意义上的第二强调色，破戒场景改用别的手法（例如反转段本身）。

## 五条冲突判例（设计系统 vs 蓝军红线，均已实际发生过）

设计系统的视觉偏好与蓝军 15 条的文案红线偶尔会正面冲突。**冲突时按下表判，不临场重新权衡**：

| 冲突 | 判给谁 | 为什么 |
|---|---|---|
| 设计系统要求全大写英文主导视觉 | **蓝军**——中文是主角，英文字号不得超过中文 | 蓝军第 5 条是文案红线，视觉偏好不能压过语言主次关系 |
| 设计系统禁止阴影，导致贴纸类品牌资产看起来"飘在画面上" | **设计系统**——不加投影，改用圆角 + 微旋转（Ciridae 案例的实际处理：圆角 14px + 旋转 −2.5°） | 这是纯视觉处理手法之争，不涉及文案红线，设计系统的形状语言应该被尊重 |
| 设计系统自带英文标签（如 `DATE`/`VENUE`/`FORM`） | **删**，除非是专有名词或行业通用词（Agent／CTO／人名这类） | 蓝军第 1 条零内部视角 + 第 5 条中文主角，装饰性英文标签对读者是零增量信息 |
| 品牌资产（logo、贴纸）处理方式 | **一律官方原始文件，不自行抠图或改色**；自带白色模切边的资产当贴纸用，不是"没抠干净"需要修 | 品牌资产的完整性优先于视觉统一性——改色抠图会破坏品牌识别 |
| SVG 内联缺 `width` | **必须显式声明 `width`** | 默认 300px 会挤坏 topbar/footer，这是纯技术约束，不是审美判断 |

**判例的共同原则：内容与身份相关的红线（语言主次、零内部视角、品牌资产完整性）永远赢；纯视觉处理手法（阴影、圆角）跟设计系统走。** 遇到不在表里的新冲突，先问这个冲突是不是关于"读者能不能看懂/品牌是否失真"——是，按蓝军判；纯粹是"好不好看"，按设计系统判。
